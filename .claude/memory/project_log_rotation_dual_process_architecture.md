Implementing Admin Dashboard → System → Log Storage & Rotation (2026-08-26, `docs/design/Design_Log_Rotation.md`) surfaced a pre-existing architectural fact that isn't obvious from reading `utils/logger.js` alone: in production (`npm run start|streaming|analysis`), `server/src/scripts/startServer.js` is a **supervisor** process that calls `openLogFile()`/`patchConsole()` on **itself**, then `spawn()`s the real Express server (`index.js`, where every `/admin/*` route lives) as a **child process**, piping the child's stdout/stderr back through `makeLineRelay()` into the one log file the supervisor owns.

**Why this matters:** `utils/logger.js` is `require()`'d independently by both processes — Node module caching is per-process, so the supervisor's `_cfg`/`_logStream` and the child's `_cfg`/`_logStream` are two completely separate copies of the same module's state. Before this feature, nothing in the child process ever called `setLogConfig()` because no runtime-mutable config existed at all. Once you add one (e.g. "let the Admin API change the log directory live"), the naive implementation — just updating the child's own `utils/logger.js` state from the route handler — silently does nothing to the actual file on disk, because the child never calls `openLogFile()`/owns the file handle. The child's copy of `utils/logger.js` is only ever used for `tailLogFile()` (reading) and display purposes.

**How to apply:** Any future feature that needs the Admin API (or anything else running inside `index.js`) to change production log-writing behavior at runtime (directory, rotation, format, whatever) MUST relay the change to the supervisor process via IPC — `stdio: [...,'ipc']` on the `spawn()` call in `startServer.js`, `process.send()` from the child, `child.on('message', ...)` in the parent. Don't assume `require('../utils/logger')` inside `index.js`/`routes/*.js` reaches the same state as the one actually writing files; verify which process calls `openLogFile()` before wiring a "live update" path. See [[project_ingest_daemon_http_unresponsive_pattern]] for another case where this codebase's multi-process topology (there: ingest-daemon vs. Express server) was the actual root cause behind a symptom that looked like a single-process bug.

Also found in the same implementation pass: `fs.createWriteStream(path)` opens its underlying fd lazily/asynchronously. Under size-based log rotation with a burst of synchronous writes, a second rotation could fire before the first rotation's freshly-reopened file existed on disk, causing `fs.renameSync()` to throw `ENOENT` on a file that "should" have existed. Fixed by using `fs.openSync(path, 'a')` first and handing that fd to `createWriteStream(null, { fd })` — any code path that reopens a log/output file after a rename-based rotation should do the same rather than assuming `createWriteStream` synchronously guarantees the file exists.

**Second bug found post-ship (2026-08-27), different class — shared-DB config scoping, not IPC.** The original implementation persisted `{ dir, maxFileSizeMB, maxFiles }` under a single fixed `settings` row id (`logConfig`), copying `activeModelConfig.js`'s pattern verbatim. That pattern is correct for `activeModelConfig` (which AI model to run is a value every server sharing a DB *should* agree on) but wrong here: `dir` names a path on *this process's own local filesystem*, so when `DB_TYPE=mongodb` and multiple physical servers intentionally share one MongoDB (a supported deployment shape, see `docs/ops/Distributed_AI_Pipeline_Setup.md`), every server fights over the same row — whichever server's Admin Dashboard was touched last silently rewrites what every other server *thinks* its own log path is. User caught this by inspecting the shipped code, not from a bug report. Same failure class as [[project_face_search_condition_sync]]'s 2026-07-15 shared-MongoDB incident — a per-instance value stored under a globally-shared key.

**Fix (v1.1):** row id is now `` `logConfig:${SERVER_ID env var or os.hostname()}` `` (computed once in a new tiny `server/src/utils/serverId.js`, required by both `logConfigService.js` and `logger.js` to avoid drift/circularity — `logConfigService.js` already requires `logger.js`, so `logger.js` cannot require `logConfigService.js` back). First read under the new per-instance id, if not found, checks for the pre-fix global `logConfig` row and adopts its values (one-time, read-only migration — legacy row is left in place, not deleted) before falling back to `server/.env` seeding. `getLogStats()` now returns `serverId` so the Admin UI can show which instance's settings are displayed. Full design: `Design_Log_Rotation.md` §3A.

**General lesson:** before copying an existing "persist to `settings` table, seed from env on first boot" pattern for a NEW config value, ask whether that value is supposed to be *the same* across every server sharing a DB (→ fixed row id is fine, e.g. `activeModels`) or is inherently *per-machine* (→ needs a per-instance key from the start, e.g. anything naming a local filesystem path, port, or hardware resource).

**Fourth bug — real production report, empirically reproduced (2026-08-27).** User reported both live streaming/analysis dashboards showed "Active File: —" / "Archived Files: 0" and Save/Rotate appeared to do nothing, despite real log content genuinely being written. Static code reading alone did not find it — reproduced by actually spawning the real `startServer.js`+`index.js` dual-process topology in an isolated sandbox (`STORAGE_PATH`/`LOG_DIR` env overrides, `AUTH_ENABLED=false`, `DB_TYPE=json` to avoid touching production Mongo, `SERVER_MODE=analysis` to skip MediaMTX/ingest-daemon) and hitting the real HTTP endpoints with curl. Root cause: `getLogStats()` read `_logDir`/`_logPath` — populated ONLY when *this* process has itself called `openLogFile()`. The Admin API child only does that opportunistically inside `setLogConfig()` when `dirChanged` happens to be true during its own lifetime; since the child seeds its own `_cfg.dir` independently at module load via the same resolution the supervisor uses, there's a real window (confirmed via repro: fresh boot, nothing ever changed) where the child's `_logDir`/`_logPath` stay empty **forever** even though the supervisor is actively writing real files at the correct path — so `GET /admin/system/logs` permanently reports an empty list on that child, and `POST rotate` (which only relays IPC to the supervisor, never touches the child's own state) is real but invisible on the dashboard. Fixed by making `getLogStats()` scan `_logDir || _cfg.dir` (matching the `effectiveDir` fallback already used) regardless of which process opened the handle — read-only, no new file handles. Re-verified with the same repro harness after the fix: correct `currentFile`/`files` on the very first GET after a fresh boot, and after a real `rotate`. Full design: `Design_Log_Rotation.md` §3C.

**Methodology lesson:** for a report of "the UI shows X but Y is actually happening," prefer spawning the REAL process topology in an isolated sandbox over re-reading the code — this bug was invisible from code review alone (the code "looks" like it should work; the bug is in when a rarely-false-until-it-matters branch condition is actually false) and took under 10 minutes to nail down empirically once reproduced, versus much longer circling on plausible-but-wrong theories (JWT expiry, MongoDB `_id` coercion, stale deploy) from reading code alone.

**Third bug found post-ship, same review (2026-08-27), fixed same day.** The `LOG_DIR` default was hardcoded `/var/log/lts` in both `logger.js` and `logConfigService.js`, with no `_WINDOWS`/`_LINUX` variant — unlike every other path-like env var in this project (`YTDLP_BIN_WINDOWS`/`_LINUX`, `INGEST_DAEMON_BIN_WINDOWS`/`_LINUX`, `MEDIAMTX_BIN_WINDOWS`/`_LINUX`, `PYTHON_EXEC_WINDOWS`/`_LINUX`). Not a crash (the existing `FALLBACK_DIR = server/logs/`, built via `path.resolve()`, always caught it) but a silently-Linux-only default. Fixed by adding `_resolveDefaultLogDir()` to `logger.js` (single source, `logConfigService.js` calls it instead of duplicating the literal): `LOG_DIR_WINDOWS`/`LOG_DIR_LINUX` (OS-specific, checked first — matches `youtubeStreamService.js#findYtDlp()`'s precedence of OS-specific over general) → `LOG_DIR` (general) → hardcoded per-OS default (`C:\ProgramData\lts\logs` / `/var/log/lts`). Full design: `Design_Log_Rotation.md` §3B.
