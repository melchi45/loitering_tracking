**STALE (2026-08-10):** the submodule/postinstall structure this memory describes (`submodules/ump-player`, `client/scripts/copyUmpPlayerAssets.js`, `client/public/media/ump/`) was removed 2026-08-04 — the player now ships as the npm package `@melchi45/rtsp-over-websocket`, imported directly by `client/src/components/RTSPOverWebSocketView.tsx` (no postinstall copy step, no `client/public/media/`). The bug/root-cause narrative below (lines describing the STAP-A depacketizer crash) is still accurate history of what broke and why; only the "where the source lives" and "how to apply a fix" guidance is outdated — see the correction at the bottom.

`client/public/media/ump/MediaSession/VideoSession/h264Session.js`'s depacketize() switch only handled NAL types 7(SPS)/8(PPS) standalone and 28(FU-A) — types 24-27 (STAP-A/STAP-B/MTAP16/MTAP24, RFC 6184 §5.7 aggregation packets) were defined in the `H264NalUnit` enum as `H264_NAL_UNSPECIFIED24..27` but had **no case at all**, falling through to `default:` which just pushed the raw aggregate payload as if it were one NAL. If a camera bundles SPS+PPS+IDR into one STAP-A (type 24) RTP packet, `sps_segment`/`pps_segment` (module-scoped closure vars) stay `null` forever for that channel, and every marker-bit frame crashes in `h264SPSParser.js` `nal_unit_extract_rbsp()` on `src.byteLength` since `src` is null. Because `mediaRouter.js`'s `spsParse()` is called on every single frame (both the I-frame branch and the P-frame `else` branch of `onVideoData`), this repeats on every frame for the affected channel only — other channels/cameras that send SPS/PPS as standalone NALs are unaffected. `RtpDataHandler` in `rtspClient.js` has no try/catch around `sendRtpData`, so the exception is uncaught but only unwinds that one channel's synchronous call stack (per-message JS event loop isolation) — explaining why only one specific camera/channel "freezes" while others in the same multiplexed WebSocket session keep working.

**Fix (2026-07-23)**: added a `H264_NAL_STAP_A` case in `h264Session.js` depacketize() that unrolls the aggregation packet (`[2-byte size][NAL]` repeated) and extracts embedded SPS(7)/PPS(8) correctly; STAP-B/MTAP16/MTAP24 now throw an explicit unsupported-type `umpError` instead of silently falling to `default`. Also renamed the misleading `H264_NAL_UNSPECIFIED24..27` enum entries to their real RFC 6184 names. Added a null-guard in `mediaRouter.js`'s `spsParse()` that throws a clear `umpError` (0x0304) instead of a bare TypeError if SPS is still unavailable, for future diagnosability.

**Historical structural note (no longer applies — see STALE banner)**: at the time of this fix, `client/public/media/ump/` was NOT hand-edited source — it was generated verbatim by `client/scripts/copyUmpPlayerAssets.js` (npm postinstall) from `submodules/ump-player/app/media/`. Any fix had to go into the submodule source first, then be re-synced. See [[project_guide_distribution_pattern]] for the general docs/skill dual-copy pattern this was an instance of.

**How to apply now (corrected 2026-08-10)**: the equivalent source today is inside the npm package at `client/node_modules/@melchi45/rtsp-over-websocket/` (installed from `github.com/melchi45/rtsp-over-websocket`, GitHub Packages) — NOT `submodules/ump-player/` (deleted). For a client-side depacketizer/parser bug (H.264/H.265 SPS/PPS/NAL parsing, RTP marker bit, mediaRouter frame assembly), a fix must be made upstream in that package's own repo and released as a new npm version — this LTS-2026 repo no longer vendors or can directly patch the player source. ingest-daemon and mediasoup still forward RTP/H.264 bytes transparently at the NAL level and do not repacketize NAL structure, so client-side parsing bugs are still not explained by anything upstream in the capture/mediasoup pipeline.
